Week 7 — AI API Integration
1. Overview of the Week
This is the signature week of this domain — you integrate a real AI API into your app. The AI feature you planned in your Week 1 Project Brief now becomes functional. You will select an API, secure the API key, build the backend service that calls the AI, and surface the result in your frontend UI. By the end of this week, users can interact with an AI-powered feature inside your live-running app.
2. What You Will Do This Week
Choose your AI API:
OpenAI (GPT-4o or GPT-4o-mini): best general-purpose quality; requires paid account with small credits.
Google Gemini (gemini-1.5-flash or gemini-1.5-pro): free tier is generous; works well for chat and summarisation.
Hugging Face Inference API: open-source models, fully free tier; use for specialised tasks (sentiment, summarisation, image captioning).
Get your API key:
OpenAI: platform.openai.com → API Keys
Google Gemini: aistudio.google.com → Get API Key
Hugging Face: huggingface.co → Settings → Access Tokens
Store API keys securely:
Add to .env as OPENAI_API_KEY, GEMINI_API_KEY, or HF_API_KEY
Verify .env is in .gitignore before any commit — confirm by running git status
Design the AI feature: exactly what the user inputs, what the AI does, what the user sees. Example features: "summarise a long document", "generate a quiz from notes", "rewrite text in a chosen tone", "AI chat assistant for a specific domain", "semantic search over user's saved items".
Build the backend AI service:
Create a new endpoint POST /api/ai/[feature] (e.g., /api/ai/summarise)
The endpoint receives user input from the frontend, constructs a prompt, calls the AI API, parses the response, and returns formatted JSON to the frontend
Add error handling — what happens if the API call fails, times out, or rate-limits
Connect AI output to frontend:
Build a frontend component that takes user input, sends it to your backend, and displays the result
Show a loading state (your Loader from Week 3) while the AI is responding
Show an error Toast if the call fails
If using streaming responses (OpenAI streaming), progressively render the response as it arrives
Write and iterate prompts: test at least 3 prompt variations for your feature. Document which one worked best and why in a PROMPTS.md file or in your README.

5. Deliverables
Deliverable 1: AI Feature Live in Your App
Feature end-to-end functional on localhost: user can submit input, see loading state, and receive AI-generated output.
Backend service secure: API key only in .env, never in committed code.
Loading state shown during API call.
Error handling shown to user on failure.
Deliverable 2: Demo Screenshot and GitHub Commit
3 screenshots of the AI feature in action:
User input screen
Loading state (mid-request)
Final AI output displayed
Include browser Network tab showing the POST /api/ai/… request with status 200.
Commit message for this week should clearly mention the AI feature (e.g., feat: integrate OpenAI summariser with loading and error states).
File name: W7_AIFeatureDemo_[InternID].pdf
Deliverable 3: Prompts Log (PROMPTS.md in Repo)
A Markdown file in your GitHub repo (PROMPTS.md at repo root, or inside /docs/) documenting:
The 3 prompt variations you tested.
Example input and output for each.
Which one worked best and why (3–4 sentences).
Any system prompt or role you used.
Deliverable 4: Mandatory Peer Code Review
Review 2 classmates' GitHub repos.
For each review, submit a 150-word structured comment covering: 1 architectural observation, 1 specific code suggestion (with file reference if possible), 1 question.
